## Run from source

```
pip install -r requirements-build.txt
python ransom_guard.py --gui
```

`requirements.txt` lists what running from source needs; `requirements-build.txt` adds the exact PyInstaller version used for releases.

To run with Python instead of the exe, the project includes a few helper files (keep them in the same folder as `ransom_guard.py`):

| File | What it does |
| --- | --- |
| `install_ransom_guard.bat` | Installs background monitoring using Python (finds Python and installs watchdog) |
| `restore_network.bat` | Restores a cut-off network, no Python needed |
| `preview_warning.bat` | Previews the full-screen warning |

> [!WARNING]
> A scheduled task installed this way runs `ransom_guard.py` and the `ransomguard` package with administrator rights from the folder they are in. Keep the project in a folder only administrators can change; see [Known security issues](README.md#known-security-issues).

## Code layout

`ransom_guard.py` only starts the program; the code is in the `ransomguard` package:

| Module | What it does |
| --- | --- |
| `config` | Version, the settings you can tune, the interface language, the user's settings |
| `winapi` | Windows plumbing: PowerShell and system programs, kernel32, processes, message boxes, known folders |
| `storage` | The log, and the state in `C:\ProgramData\RansomGuard` that only administrators can change |
| `folders` | Which folders are watched |
| `canary` | The hidden canary files |
| `detection` | Telling encryption from everyday work; the file-event handler |
| `processes` | Destructive commands and the process monitor |
| `response` | What happens on a trigger: pausing programs, the full-screen warning |
| `defender` | Microsoft Defender scans and the download scanner |
| `network` | Cutting the network off and restoring it |
| `install` | Scheduled tasks, install, uninstall, the health check |
| `updates` | New versions from GitHub |
| `gui` | The control panel |
| `app` | The monitor's main loop and the command line |

Modules refer to each other as `module.name` (`network.disconnect_network()`), never `from module import name` (only `tr`, `log` and `norm` are imported by name). That way replacing a name in its module, as the tests do, takes effect everywhere. The tests reach the whole program through one object, `rg`, which finds the module each name lives in.

## Build

```
build.bat
```

The built file is `dist\RansomGuard.exe`. To use a Python that is not on PATH, set `PYTHON` first, e.g. `set PYTHON=C:\Python314\python.exe`.

- `build.bat` packs `icon.ico` into the exe. Without it, the window, taskbar and desktop shortcut show PyInstaller's default icon.
- It then runs `check_build.py`, which fails the build if the exe lacks any module of the `ransomguard` package or the Tcl/Tk files the control panel needs. PyInstaller only warns about that, and such an exe doesn't start at all. That happened to v1.7.1, built with Python 3.14.9, whose Tcl/Tk 9 files PyInstaller 6.21 can't pack; releases use Python 3.14.6.

The icon (`icon.ico` / `icon.png`) is generated by `make_icon.py` (needs `pip install pillow`). To change the icon, edit that file and run it again.

## Tests

Python's built-in `unittest`; `pytest` runs them too:

```
python -m unittest discover -s tests -v
```

The tests only use temporary folders and never touch your files, the network settings, the internet or the installed program. This is enforced for the whole suite:

- user folders, the app folder and the install folder point into a temporary sandbox;
- a test that reaches the PowerShell commands for network adapters, the firewall or scheduled tasks, `ipconfig` / `netsh` / shutdown, the internet or the full-screen warning without replacing it fails instead;
- only processes the tests started themselves can be paused.

Some tests use read-only Windows features for real: watching new processes through WMI, Defender scans of temporary files, and reading scheduled tasks.

## Publishing a new version

Releases are built and published by GitHub Actions, never uploaded by hand:

1. Change `VERSION` in `ransomguard/config.py`, e.g. to `"1.7.6"`, and write the release notes in `release-notes/v1.7.6.md`.
2. Run the tests, commit and push. The [CI workflow](.github/workflows/ci.yml) runs the checks, the tests and a build on every push to a branch and every pull request.
3. Tag the commit and push the tag:

   ```
   git tag v1.7.6
   git push origin v1.7.6
   ```

4. The [release workflow](.github/workflows/release.yml) checks that the tag matches `VERSION`, runs the tests, builds the exe, signs its attestation, publishes the release (as a draft first, so the exe is attached before the release becomes immutable) and adds a "please update" notice to the previous release's notes.

Releases from v1.7.0 on are immutable: once published, their files and tags can't be changed, so a mistake means a new version number, and their exe stays downloadable. The download button in the README always points to the latest version, so it never needs editing.
